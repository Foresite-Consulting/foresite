# ADR 0003: People-counter ingest (HTTP push, per-device auth, dedupe)

Status: Proposed (for Lachlan)
Date: 19 Oct 2026

## Context

The first client wants live people-in-venue counts. The recommended counter is the Milesight VS135 (4G, time-of-flight). It pushes JSON to up to 8 recipients over HTTP(S) with a username and password, or over MQTT(S) with client certificates, periodically or on change, and re-sends buffered data after an outage (vendor links and exact sections in `packages/connectors/src/counters/milesight/RUNBOOK.md`). Other venues may use other counters, so the intake must be vendor-neutral.

Constraints from `CLAUDE.md`: devices post to an authenticated ingest endpoint and never hold database credentials; Supabase (Sydney) and Vercel; timestamps in UTC, trading day assigned later; synthetic data only; anything not in vendor docs is `UNVERIFIED`. The trading-day model is being built in parallel, so this PR stores raw UTC intervals only.

## Options

**Transport and device auth**

1. **HTTPS push with HTTP Basic, one credential per device.** Pros: what the device's HTTP(S) recipient supports (User/Password); works on Vercel with no extra infrastructure; easy to rotate. Cons: a shared secret (not a certificate); the device's exact auth behaviour is UNVERIFIED (Basic vs Digest, pre-emptive or challenged). Cost: none.
2. **MQTTS with client certificates.** Pros: mutual TLS, no shared secret; QoS 1/2 delivery. Cons: needs a broker (Vercel functions cannot hold MQTT connections), a bridge into the app, and certificate issuance per device. Cost: a hosted broker subscription in the client's name.
3. **Vendor cloud (Milesight Development Platform webhooks).** Pros: vendor handles devices. Cons: data passes through a third party overseas; another account; less control. Cost: possible subscription.

**Secret hashing:** scrypt (Node `crypto`, no native build) vs argon2id (needs a native or WASM package) vs plain SHA-256 (adequate for 238-bit random secrets but weaker if a short secret is ever used).

**Dedupe rule** for a re-sent interval with different counts: first write wins; reject the second; latest device timestamp wins.

**Rate-limit store:** in-memory per instance; Postgres table; a shared key-value store (e.g. Upstash Redis via the Vercel Marketplace).

## Decision

- **Option 1: HTTPS push, HTTP Basic per device** at `POST /api/ingest/counters/<provider>` (`milesight` first). Username = Foresite device id, password = a 40-character random secret generated by `npm run device:create -w apps/web` and shown once. Production refuses requests whose `x-forwarded-proto` is not `https`. 401 responses carry a `WWW-Authenticate: Basic` challenge in case the device waits for one. MQTTS stays the fallback if U1 in the runbook fails on a real device.
- **scrypt** (N=2^14, r=8, p=1, 16-byte salt, 32-byte key), parameters stored with each hash so they can be raised. Constant-time comparison. Every attempt runs exactly two scrypt checks (two rotation slots; a dummy hash fills empty slots and unknown devices), so timing does not reveal whether a device exists or is rotating. Secrets live in their own table (`counter_device_credentials`) that will never get a read policy.
- **Verified-credential cache:** after a credential passes scrypt, an HMAC tag of (device id, secret, current hashes) under a per-process random key is kept for 10 minutes, so the same device skips scrypt on later requests. Wrong secrets and unknown devices always take the full path, so the shortcut reveals nothing without the secret; changing the stored hashes invalidates it; `active` is read on every request. Load check on 2 vCPUs, 50 synthetic devices, production build with in-memory storage: without the cache ≈ 6–7 requests/s (scrypt-bound); with it, 1,000 requests at concurrency 50 in 3.7 s (p50 162 ms, p95 305 ms).
- **Rotation:** up to two active secrets per device; add the new one, update the device, drop the old one once logs show slot 2 in use. The generated SQL raises an error, changing nothing, unless exactly one row is updated (review F8), so a mistyped device id or a second step 1 cannot leave an operator holding a secret the database never stored.
- **Dedupe:** a reading is unique on `(device_id, entry_point_id, interval_start, interval_end)`. Same counts → duplicate, nothing changes. Different counts → a conflict: the later `device_reported_at` wins, a tie goes to the later arrival, and both versions are kept in a `reading_conflict` event. For Milesight periodic reports `device_reported_at` is the interval end (the payload has no separate generation time), so in practice the latest arrival wins. Raw bodies are also unique per `(device_id, sha256)`. Postgres: `insert … on conflict do nothing`, then `select … for update` on a clash, in one transaction per request.
- **Only periodic line reports become readings.** Trigger reports carry the same crossings and would double count; they are accepted (200) and counted as `ignored`. Region data is kept in the raw table only. Occlusion alarms become events.
- **Clock sanity** against receipt time: interval end > 10 min in the future → rejected; start > 30 days ago (`INGEST_MAX_AGE_DAYS`) → rejected; end > 15 min ago → stored and flagged `late`. Rejected readings still get a 2xx response (and an event) so the device does not retry them forever.
- **Limits:** 64 KB body cap (checked on `Content-Length` before auth and while streaming after), `application/json` only, per-device token bucket (burst 60, 1/s) after auth, and failed-login buckets checked before scrypt runs. 429 carries `Retry-After`.
- **Failed-login throttle (review F2):** the strict bucket (10/min) is keyed on client address **and** claimed device id, so one misconfigured counter behind a shared address (carrier-grade NAT is normal on Australian 4G) cannot lock out the other counters at that address. A malformed `Authorization` header gets a key of its own. A looser per-address bucket (100/min, `INGEST_AUTH_FAILURES_PER_ADDRESS_PER_MINUTE`) is the backstop against spraying many device ids from one address. A credential already in the verified-credential cache (an HMAC of id and secret; never the secret) skips both checks; if it then fails, its cache entry is dropped. Trade-off: while the backstop is exhausted, a good device that this instance has not yet verified (e.g. after a cold start) also waits; it recovers within a minute of the spray stopping.
- **Hostile bodies (review F4, F7):** right after `JSON.parse`, an iterative walk refuses nesting deeper than 32 levels and strings PostgreSQL `jsonb` cannot hold (`\u0000`, unpaired surrogates) with 400 `invalid_json`, so attacker-controlled input cannot cause a 5xx at the store. A client that closes the connection mid-body gets 400 `body_aborted` (logged as a warning with the request id).
- **Line mapping (review F1):** every line must land on its own entry point. `device:create` refuses a `--line` equal to `--entry`, a repeated line or entry point, or the reserved `<entry>:line-<n>` form; the adapter refuses a report whose lines resolve to the same entry point with 400 `duplicate_entry_point`, instead of letting one line overwrite another's counts.
- **Data minimisation (privacy):** device and SIM identifiers are not needed for counting, so the adapter's `minimise` step removes them before anything is stored or mapped: Milesight `network_info` (ICCID, IMEI, cell ID, LAC), `nodeDeviceInfo`, `device_mac`/`mac`, `ip_address`, and any ICCID/IMEI/IMSI/MSISDN/cell-id/LAC key anywhere in the body. The raw row keeps only the names of the keys removed (`metadata.stripped_keys`), never their values. `payload_hash` is still the SHA-256 of the exact bytes received, so re-sends deduplicate; a hash of a whole body does not reveal the identifiers. The runbook also says to switch network info off on the device.
- **Overlapping intervals (review F5, flag only):** intervals that overlap at one entry point (e.g. the reporting period changed from 5 to 60 minutes) are stored as distinct rows; a newly accepted reading that overlaps stored ones writes an `overlap_detected` event (entry point, interval, number overlapped) in the same transaction. Not a rejection. A check constraint caps an interval at 24 hours, which bounds the lookup to a range scan of the natural-key index. See Open decisions.
- **Rate-limit store: in-memory for now**, behind a `RateLimiter` interface. On Vercel each instance has its own buckets, so the limit is per device per instance. A shared store is needed for a hard limit; which one is **for Lachlan** (UNVERIFIED: cost and latency of Upstash vs a Postgres table on the Supabase pooler).
- **Storage:** `IngestRepository` with an in-memory adapter (tests, local, Playwright) and a PostgreSQL adapter (driver-agnostic; production uses `postgres` 3.4.9, `prepare: false` for the transaction pooler). Production refuses in-memory storage on Vercel and refuses database TLS without certificate verification (`sslmode=verify-full` or `DATABASE_CA_CERT`).
- **Migration** `db/migrations/0001_counter_ingest.sql`: `venue_id` on every table (composite foreign keys keep it equal to the device's venue), RLS enabled with no policies (default deny for `anon`/`authenticated`, which also lose their table privileges and their privileges on the three identity sequences, review F6), a check that every stored secret hash is in the scrypt format, the ingest server connecting as owner (see Open decisions, F3). Read policies are a TODO for the auth PR, using Supabase Auth (`auth.uid()`) and a venue membership table with roles owner/manager/supervisor/staff, as sketched in the migration.
- **Dependencies:** `postgres` 3.4.9 (runtime, zero dependencies, Unlicense) and `@electric-sql/pglite` 0.5.8 (dev only, Apache-2.0, in-process PostgreSQL so CI tests the real SQL without Docker).

## Open decisions (for Lachlan)

Raised by the independent review of PR 3. Documented here, not built, except the F5 flag.

### F3: a least-privilege database role for ingest

Today the ingest server connects as the table owner, which bypasses RLS and can do anything to the five tables. **Recommendation: do it in the auth PR**, when policies arrive anyway: a dedicated login role (e.g. `counter_ingest`, through the Supabase pooler) with only what the endpoint uses, plus RLS policies for that role (it is not the owner, so RLS applies to it). The grants below were checked against the repository code in PGlite (find device, ingest with a conflict and a duplicate, reject a payload); identity columns need no sequence privileges.

```sql
grant select (device_id, provider, venue_id, entry_point_id, line_entry_points, vendor_serial, active)
  on counter_devices to counter_ingest;
grant select (device_id, venue_id, secret_hashes) on counter_device_credentials to counter_ingest;
-- select on the conflict target and RETURNING columns is needed by insert … on conflict … returning id
grant insert (venue_id, device_id, provider, payload_hash, payload, received_at, parse_status, error_code, metadata),
      select (id, device_id, payload_hash)
  on counter_raw_payloads to counter_ingest;
grant insert (venue_id, device_id, entry_point_id, source_line, interval_start, interval_end, count_in,
              count_out, occupancy, device_reported_at, received_at, raw_payload_hash, clock_flag),
      select (id, device_id, entry_point_id, interval_start, interval_end, count_in, count_out, occupancy,
              device_reported_at, received_at, raw_payload_hash, clock_flag, revision),
      update (count_in, count_out, occupancy, device_reported_at, received_at, raw_payload_hash,
              clock_flag, source_line, revision, updated_at)
  on counter_readings to counter_ingest;
grant insert (venue_id, device_id, event_type, occurred_at, detail) on counter_ingest_events to counter_ingest;
-- Policies for that role: select on devices and credentials; insert/select on raw payloads and readings,
-- update on readings; insert only on events. No delete anywhere; no read of raw payload bodies or events.
```

The `listReadings`/`listEvents`/`listRawPayloads` helpers are for tests and operators and would not work under this role (by design). Supabase specifics (creating login roles, pooler user naming such as `role.project-ref`) are UNVERIFIED until the first deploy.

### F5: overlapping intervals

Overlapping intervals at one entry point are stored as distinct rows; summing them would double count. Options:

1. **Exclusion constraint** (`btree_gist`, `exclude using gist (device_id with =, entry_point_id with =, tstzrange(interval_start, interval_end) with &&)`). Pros: impossible to store an overlap. Cons: a device whose reporting period changes loses data (the second shape is refused, and the device retries forever unless we answer 2xx); needs an extension; makes the dedupe path more complex.
2. **Detection in the trading-day join** (e.g. prefer the finest interval, or the latest revision, per entry point and time). Pros: no data lost; the rule lives where totals are computed. Cons: every consumer must use the join, not raw sums.

**Recommendation: option 2**, with the cheap flag now: **built in this PR**, an `overlap_detected` ingest event (not a rejection) written whenever a new reading overlaps stored ones, so the overlap is visible before the join exists. The join's rule is for the trading-day PR.

### Retention for raw payloads and events (question for the privacy adviser)

`counter_raw_payloads` holds request bodies (now without device or SIM identifiers) for replay; `counter_ingest_events` gets one summary row per request (≈ 288 per device per day at 5-minute intervals) plus conflicts, alarms and rejections. Neither holds personal information about venue guests (counts only), but raw bodies could carry fields a firmware update adds. Proposed for the adviser's view: raw payloads 90 days (long enough to find and replay a mapping bug), events 13 months (a year-on-year comparison), readings kept for the life of the engagement. Deletion by a scheduled job once agreed. Not built.

## Consequences

- Easier: adding a counter vendor is a new adapter in `packages/connectors/src/counters/<vendor>/` plus a registry line; the endpoint, auth, limits and storage are shared.
- Easier: replaying a mapping fix, because every authenticated JSON body is stored (minus device and SIM identifiers) before mapping.
- Harder: the endpoint is only as strong as one shared secret per device over TLS. Mitigated by long random secrets, per-device revocation, rotation and serial pinning (`vendor_serial`).
- The trading-day join is a follow-up: readings carry UTC `interval_start`/`interval_end` only.
- Follow-ups: shared rate-limit store; a feed-health view (`GET /api/ingest/counters/status`) protected by the auth PR; "no data for N minutes" alerts; a raw-payload replay script; retention (see Open decisions); run the optional live-Postgres tests in CI with a service container.
- Migration numbering: this is `0001`; if another branch also adds a `0001_*`, the second to merge renumbers before merge.
- UNVERIFIED, to confirm on the first device and deploy: U1–U16 in the runbook (auth scheme, content type, error/retry behaviour, retransmission pace, Connection Test body, `capacity_counted` meaning, password limits, recipient count); Vercel's `x-forwarded-proto`/`x-real-ip` handling; the Supabase CA certificate and pooler behaviour with postgres.js.
- Reusable in the core: all of it. Client-specific: device registrations and line mappings (data, not code).

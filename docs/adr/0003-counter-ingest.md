# ADR 0003: People-counter ingest (HTTP push, per-device auth, dedupe)

Status: Proposed (for Lachlan)
Date: 19 Oct 2026

## Context

The first client wants live people-in-venue counts. The recommended counter is the Milesight VS135 (4G, time-of-flight). It pushes JSON to up to 8 recipients over HTTP(S) with a username and password, or over MQTT(S) with client certificates, periodically or on change, and re-sends buffered data after an outage (vendor links and exact sections in `packages/connectors/src/counters/milesight/RUNBOOK.md`). Other venues may use other counters, so the intake must be vendor-neutral.

Constraints from `CLAUDE.md`: devices post to an authenticated ingest endpoint and never hold database credentials; Supabase (Sydney) and Vercel; timestamps in UTC, trading day assigned later; synthetic data only; anything not in vendor docs is `UNVERIFIED`. The trading-day model is being built in parallel, so this PR stores raw UTC intervals only.

## Options

**Transport and device auth**

1. **HTTPS push with HTTP Basic, one credential per device.** Pros: what the device's HTTP(S) recipient supports (User/Password); works on Vercel with no extra infrastructure; easy to rotate. Cons: a shared secret (not a certificate); the device's exact auth behaviour is UNVERIFIED (Basic vs Digest, pre-emptive or challenged). Cost: none.
2. **MQTTS with client certificates.** Pros: mutual TLS, no shared secret; QoS 1/2 delivery. Cons: needs a broker (Vercel functions cannot hold MQTT connections), a bridge into the app, and certificate issuance per device. Cost: a hosted broker subscription in the client's name.
3. **Vendor cloud (Milesight Development Platform webhooks).** Pros: vendor handles devices. Cons: data passes through a third party overseas; another account; less control. Cost: possible subscription.

**Secret hashing:** scrypt (Node `crypto`, no native build) vs argon2id (needs a native or WASM package) vs plain SHA-256 (adequate for 238-bit random secrets but weaker if a short secret is ever used).

**Dedupe rule** for a re-sent interval with different counts: first write wins; reject the second; latest device timestamp wins.

**Rate-limit store:** in-memory per instance; Postgres table; a shared key-value store (e.g. Upstash Redis via the Vercel Marketplace).

## Decision

- **Option 1: HTTPS push, HTTP Basic per device** at `POST /api/ingest/counters/<provider>` (`milesight` first). Username = Foresite device id, password = a 40-character random secret generated by `npm run device:create -w apps/web` and shown once. Production refuses requests whose `x-forwarded-proto` is not `https`. 401 responses carry a `WWW-Authenticate: Basic` challenge in case the device waits for one. MQTTS stays the fallback if U1 in the runbook fails on a real device.
- **scrypt** (N=2^14, r=8, p=1, 16-byte salt, 32-byte key), parameters stored with each hash so they can be raised. Constant-time comparison. Every attempt runs exactly two scrypt checks (two rotation slots; a dummy hash fills empty slots and unknown devices), so timing does not reveal whether a device exists or is rotating. Secrets live in their own table (`counter_device_credentials`) that will never get a read policy.
- **Verified-credential cache:** after a credential passes scrypt, an HMAC tag of (device id, secret, current hashes) under a per-process random key is kept for 10 minutes, so the same device skips scrypt on later requests. Wrong secrets and unknown devices always take the full path, so the shortcut reveals nothing without the secret; changing the stored hashes invalidates it; `active` is read on every request. Load check on 2 vCPUs, 50 synthetic devices, production build with in-memory storage: without the cache ≈ 6–7 requests/s (scrypt-bound); with it, 1,000 requests at concurrency 50 in 3.7 s (p50 162 ms, p95 305 ms).
- **Rotation:** up to two active secrets per device; add the new one, update the device, drop the old one once logs show slot 2 in use.
- **Dedupe:** a reading is unique on `(device_id, entry_point_id, interval_start, interval_end)`. Same counts → duplicate, nothing changes. Different counts → a conflict: the later `device_reported_at` wins, a tie goes to the later arrival, and both versions are kept in a `reading_conflict` event. For Milesight periodic reports `device_reported_at` is the interval end (the payload has no separate generation time), so in practice the latest arrival wins. Raw bodies are also unique per `(device_id, sha256)`. Postgres: `insert … on conflict do nothing`, then `select … for update` on a clash, in one transaction per request.
- **Only periodic line reports become readings.** Trigger reports carry the same crossings and would double count; they are accepted (200) and counted as `ignored`. Region data is kept in the raw table only. Occlusion alarms become events.
- **Clock sanity** against receipt time: interval end > 10 min in the future → rejected; start > 30 days ago (`INGEST_MAX_AGE_DAYS`) → rejected; end > 15 min ago → stored and flagged `late`. Rejected readings still get a 2xx response (and an event) so the device does not retry them forever.
- **Limits:** 64 KB body cap (checked on `Content-Length` before auth and while streaming after), `application/json` only, per-device token bucket (burst 60, 1/s) after auth, and a failed-login bucket per client address (10/min) checked before scrypt runs. 429 carries `Retry-After`.
- **Rate-limit store: in-memory for now**, behind a `RateLimiter` interface. On Vercel each instance has its own buckets, so the limit is per device per instance. A shared store is needed for a hard limit; which one is **for Lachlan** (UNVERIFIED: cost and latency of Upstash vs a Postgres table on the Supabase pooler).
- **Storage:** `IngestRepository` with an in-memory adapter (tests, local, Playwright) and a PostgreSQL adapter (driver-agnostic; production uses `postgres` 3.4.9, `prepare: false` for the transaction pooler). Production refuses in-memory storage on Vercel and refuses database TLS without certificate verification (`sslmode=verify-full` or `DATABASE_CA_CERT`).
- **Migration** `db/migrations/0001_counter_ingest.sql`: `venue_id` on every table (composite foreign keys keep it equal to the device's venue), RLS enabled with no policies (default deny for `anon`/`authenticated`, which also lose their table privileges), the ingest server connecting as owner. Read policies are a TODO for the auth PR, using Supabase Auth (`auth.uid()`) and a venue membership table with roles owner/manager/supervisor/staff, as sketched in the migration.
- **Dependencies:** `postgres` 3.4.9 (runtime, zero dependencies, Unlicense) and `@electric-sql/pglite` 0.5.8 (dev only, Apache-2.0, in-process PostgreSQL so CI tests the real SQL without Docker).

## Consequences

- Easier: adding a counter vendor is a new adapter in `packages/connectors/src/counters/<vendor>/` plus a registry line; the endpoint, auth, limits and storage are shared.
- Easier: replaying a mapping fix, because every authenticated JSON body is stored before mapping.
- Harder: the endpoint is only as strong as one shared secret per device over TLS. Mitigated by long random secrets, per-device revocation, rotation and serial pinning (`vendor_serial`).
- The trading-day join is a follow-up: readings carry UTC `interval_start`/`interval_end` only.
- Follow-ups: shared rate-limit store; a feed-health view (`GET /api/ingest/counters/status`) protected by the auth PR; "no data for N minutes" alerts; a raw-payload replay script; retention for `counter_raw_payloads` and `counter_ingest_events` (one summary event per request ≈ 288 rows per device per day at 5-minute intervals); run the optional live-Postgres tests in CI with a service container.
- Migration numbering: this is `0001`; if another branch also adds a `0001_*`, the second to merge renumbers before merge.
- UNVERIFIED, to confirm on the first device and deploy: U1–U16 in the runbook (auth scheme, content type, error/retry behaviour, retransmission pace, Connection Test body, `capacity_counted` meaning, password limits, recipient count); Vercel's `x-forwarded-proto`/`x-real-ip` handling; the Supabase CA certificate and pooler behaviour with postgres.js.
- Reusable in the core: all of it. Client-specific: device registrations and line mappings (data, not code).
